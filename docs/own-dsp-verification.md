### RISK/EFFORT PESSIMIST. I re-checked the brief's load-bearing claims against Microsoft Learn, the Equalizer APO source (including a local copy of FilterEngine.cpp on disk), the ViPERDSP/ViPER4Windows repos, and this machine's registry and filesystem.

VERDICT: the brief is technically accurate on most DSP and most Microsoft-API detail, but it is wrong on two structural points, it is built on a project that does not exist at the stated path, and it systematically underprices the non-DSP work.

THE TWO STRUCTURAL ERRORS

1. It mislabels the registry PIDs that ViPER4Windows actually uses, and in doing so misses the single most important platform feature for this project. FxProperties ",13/,14/,15" are NOT PKEY_FX_StreamEffectClsid/ModeEffectClsid (those are ",5/,6/,7"). They are PKEY_CompositeFX_StreamEffectClsid / ModeEffectClsid / EndpointEffectClsid — REG_MULTI_SZ *lists* of CLSIDs, present since Windows 10 1803, whose whole purpose is chaining several APOs in one slot. Microsoft's own INF sample concatenates two CLSIDs (SWAP + DELAY). I confirmed on this machine that endpoint {7fbb7c92-3348-419d-8245-48a9e7e50143} carries ViPER's CLSIDs at ,13 and ,14. Consequence: the brief's entire "we must displace Equalizer APO and CoCreateInstance it as a child, copying DeviceAPOInfo.cpp's backup/restore" design is the hard way. There is a documented, supported list mechanism for coexistence. It is worth one afternoon of empirical testing before any of the backup/restore machinery gets written.

2. It over-generalizes the SeCreateGlobalPrivilege restriction into "no Global\ event/mutex/semaphore either." Microsoft limits the privilege check to file-mapping and symbolic-link objects. A non-elevated GUI can create Global\ named events, mutexes, semaphores and waitable timers. The conclusion (invert ownership, or use a named pipe) still stands for the shared-memory section, but the brief's stated reason is broader than the source supports.

THE FOUNDATIONAL PROBLEM

"PeaceQT" does not exist at I:\Qt\PeaceQT. Test-Path returns False. I:\Qt contains DreamDSP and reference. The live Equalizer APO config includes dreamdsp.txt, whose first line is "# Generated by DreamDSP 0.1.0 -- edits will be overwritten." Every brief claim about existing files (src/platform/LoopbackCapture.cpp, src/platform/ApoLocator.cpp, AudioDevices.cpp, "PeaceQT's existing src/core vs src/app split") is unverifiable and possibly fabricated. Also, the prior agent's scratchpad "eqapo.log" is a SourceForge HTML error page, not a log — so at least one cited "local verification" is junk. Treat "verified on this machine" labels in the brief with suspicion; I re-verified the ones that mattered.

WHAT BREAKS THE AUDIO SYSTEM (worse than the brief says)

audiodg.exe is a single process hosting every APO on the machine. This box has at least four third-party APO vendors registered across endpoints (Equalizer APO on pid 1/2 of the default endpoint, ViPER4Windows {FA38205F-...} on ,5 across six endpoints and on ,13/,14 of another, plus Bongiovi). A null deref in DreamDSP's APOProcess does not "stop the user's audio" — it takes down every other vendor's DSP at the same time, and the user has no working audio through which to be told. The 10-failure counter that flips PKEY_Endpoint_Disable_SysFx=1 is per-endpoint and covers SFX/MFX/EFX collectively; a dev crash loop silently disables Equalizer APO and ViPER too, and Windows never explains why.

Second-order coupling the brief missed entirely: this machine only loads unsigned APOs because DisableProtectedAudioDG=1, and Equalizer APO's installer set it. If the user ever uninstalls Equalizer APO, its uninstaller can clear that key and DreamDSP's unsigned DLL stops loading — a failure with no visible cause and no relationship to anything the user did to DreamDSP.

WHAT THE EFFORT ESTIMATE MISSES

The DSP is the easy 20%. Dattorro, a Giannoulis compressor and an ADAA tanh stage are a few weekends and the brief's math for them checks out. The other 80% is: format negotiation across every rate/channel/mask the endpoint offers; multiple simultaneous instances in one audiodg (render + capture + several endpoints) with no shared mutable state; AERT_Allocate/VirtualLock for a non-paged process path; denormal control that does not disturb other APOs sharing the thread; an elevated installer plus an audiosrv bounce that momentarily kills audio for every app; a persistent elevated watchdog to re-apply registration after feature updates rotate endpoint GUIDs (this is Equalizer APO's dominant support load after fourteen years and one dedicated maintainer); an out-of-band recovery path — a .reg file and a Safe Mode procedure — because the user cannot hear the app tell them it broke; and an offline bit-exact harness so DSP is never first executed inside audiodg. Budget the infrastructure, not the algorithms.

It recommends "ship your DSP as a VST loaded by Equalizer APO's VSTPlugin command" as the lowest-risk first milestone, while separately establishing that every config.txt write destroys and re-instantiates every filter — so a reverb-decay knob cuts the tail and a compressor loses its envelope on every slider move. It also says ViPERDSP is "a working, buildable C++ reference... BOTTOM LINE ON ARCHITECTURE

Writing the APO is the right technical answer and is achievable solo — ViPER4Windows proves it in 2026. But the honest framing to the user is: Microsoft's supported model explicitly excludes driverless third-party APOs ("does not allow for an APO to be registered globally and used by multiple different drivers"), so this is permanently unsupported-but-functional territory whose maintenance cost is open-ended and whose failure mode is system-wide silent audio loss affecting other vendors' software. Before committing, prototype exactly two things: whether the CAPX property-store notification path works for a manually-registered APO, and whether CompositeFX list registration lets DreamDSP sit alongside Equalizer APO. Those two experiments decide the whole design and neither has been run.
